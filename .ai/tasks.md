## TASK-029: Fix anti-passback duplicate-scan race (attendance.service.ts:242-258)
- Status: done (2026-09-04). **Concurrency bug — "تخطي نافذة منع التمرير السريع (Double Scan)".** `recordCheckIn` read `lastVisit` and compared the duplicate `duplicateWindowSeconds` OUTSIDE the `db.transaction`, then inserted attendance (and consumed a session credit) inside it. Two rapid scans (~50ms apart / two devices) could both read the same last visit before either insert committed → both pass → two identical check-ins and a double session credit consumption.
- Fix: moved the last-visit read + `secondsAgo < windowSeconds` duplicate check **inside** the write transaction (BEGIN IMMEDIATE) so read + compare + insert are atomic on the connection. On a duplicate the body throws a module-level `CHECKIN_DUPLICATE_SENTINEL` (rolls back) which the outer try/catch swallows and converts into the existing `kind:"duplicate"` result — no client error leak. NOTE: session double-consumption was already independently guarded by `consumeSession`'s conditional `UPDATE ... WHERE sessions_used < sessions_total` (throws CONFLICT); the moved check adds the attendance-duplicate protection.
- Tests: existing "flags duplicate scans within the configured window" now traverses the in-transaction path; added "double scanning a session-plan member within the window consumes only ONE session" (rapid triple scan → success + 2 duplicates + `sessions_used === 1`). Verify: `tests/cards.checkin.test.ts` + `reception` + `part4-ops` pass; `npm run typecheck` + `typecheck:server` clean; full `npm test` **403/403** (33 files). No schema/perm/audit changes. ## TASK-028: Fix class-booking capacity race condition (classes.service.ts:366-381)

Two concurrent bookings for the last seat could both read the same free count (e.g. 9/10) and both insert → 11 booked with no `overrideCapacity`.

## TASK-027: Fix phantom full-day extension on same-day freeze/unfreeze (subscriptions.service.ts:715-718)
- Status: done (2026-09-04). **Security/logic bug — "فك التجميد في نفس اليوم يمدد اشتراك العضو يومًا كاملًا بلا مقابل".** The `actualFrozenDays` calculation used `diffDaysKeys(start_date, today) + 1` (inclusive endpoints). When a freeze starts today and is unfrozen the same day (`today === start_date`), `0 + 1 = 1` → the subscription's end date gets a free +1 day; a receptionist repeating freeze/unfreeze 3× inflated expiry by 3 days.

The audit line now reuses the same computed value instead of inlining the old expression.
- Tests (`tests/subscriptions.freeze.enhanced.test.ts`): corrected the two same-day tests to assert the new 0-day contract; added "unfreezing a freeze that started on a previous day extends by the elapsed days" (backdated start → spans yesterday+today = +2) and the reported-exploit regression "repeated same-day freeze/unfreeze does NOT inflate the expiry" (3× cycle → end_date unchanged, frozen_days=0).
