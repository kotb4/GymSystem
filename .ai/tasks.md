## TASK-040: Backup/restore file-archive hardening — real verify, safe fail-fast restore, E2E round trip (ADR-024)
- Status: done (2026-09-05). Root-caused & fixed two writer/reader defects in the `.gymbak` Files/ archive (ADR-018 §7), added a real verification layer, and made restore refuse corrupt/incomplete archives instead of silently dropping file assets. No encryption, no UI changes.
- **Root cause #1 — trailer never found.** Reader looked at a fixed `bytes.length - 24`, but the layout is `[sqlite][magic 16B "GYMBAK-FILES-V1\n"][size 8B][archive]`, so the magic actually sits at `bytes.length - 8 - archiveLength - 16` — every trailer-bearing backup was misclassified as legacy and its file assets silently dropped on restore.
- **Root cause #2 — broken size encoding.** Writers used `value >>> (8 * i)`, which wraps modulo 32 in JS for `i >= 4`, storing `L + (L << 32)` (both 32-bit halves equal L). Debug hexdump showed `[magic][02 00 00 00][02 00 00 00][00 00]` for size-2 archives.
- **`server/backups.ts` rewrite:**
  - `extractFilesArchive` — magic via `Buffer.lastIndexOf`; full 64-bit LE read without bitwise wrap; recovers L when high half is 0 (new writer) or equals low half (old-writer artifact); **exact-EOF validation** gates every accepted trailer so wrong recovery can never be misread. Writer now emits the size as two `writeUInt32LE` halves.
  - `parseFilesArchiveStrict` + `ArchiveCorruptError` — strict entry-header parsing (magic per entry, size±4 padding, name length sanity).
  - `buildFilesArchive` returns real counts `{bytes, expected, archived, skipped}`; `createServerBackup` returns `formatVersion:1`, `fileAssetsIncluded/Expected/Count/Missing`, `fullyVerified`.
  - `verifyBackupSnapshot(bytes)` — pure classifier `ok | missing_files | corrupt` (integrity probe on a sealed temp copy + manifest sha256 + file-presence), no live-state mutation.
  - `importDatabaseBytes` — fail-fast: trailer → sealed-copy integrity probe → manifest verify → files-present check; corrupt/truncated ⇒ `VALIDATION errors.backupArchiveCorrupt`, DB-references-missing-files ⇒ `errors.backupFilesIncomplete` (old "restore DB only, warn" behavior dropped). Success path snapshots the CURRENT DB+Files as a protective `.gymbak`, stages the tree, swaps the **Files** tree first (`.restore-old-<ts>`, swap failure aborts with DB untouched), then adopts the DB.
  - Extended `RestoreFileReport` (formatVersion, fileAssetsExpected/Stored/Verified, filesRestored/filesMissing, integrityStatus, fullyVerified).
- **`server/files.service.ts`:** exported `isSafeRelativePath(input)` — structural guard (no leading `/`, no `..`, no backslash tricks, no drive prefixes, no control chars) applied to every stored entry name before staging/extract.
- **i18n:** `errors.backupArchiveCorrupt` ({reason}) + `errors.backupFilesIncomplete` ({missing, mismatched, files}); fixed the over-indented pre-existing backup keys.
- **Tests:** new `tests/backup-restore-integration.test.ts` (4): round trip (seed member+photo `FF D8 FF E0` JPEG+PDF via `saveRawBytes`, `UPDATE members SET photo_file_id` mirroring `setMemberPhoto`, backup → verify → destroy data dir incl. `Files/` → restore on fresh install with its owner set up → member/photo/report bytes + `files` registry identical; legacy owner-only backup restores `fileAssetsIncluded:false`; truncated + end-marker-flip + content-flip + sqlite-only-with-file-refs all rejected leaving DB untouched; compressor/dedup shape sanity). Also `verifyBackupSnapshot` classify test + `isSafeRelativePath` table test. The recovery path (old-writer duplicate-half size) is exercised via the corrupt-content/integrity tests. Debug test `tests/_debug-backup.test.ts` created then deleted.
